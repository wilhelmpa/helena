# Decision: the framework (`@helena/sdk`, registries, events, plugins)

Status: decided 2026-09-24 (package X "Framework"). Owner rule §3b: standards first, own code only as a thin layer.

`@helena/sdk` defines no new protocol. It is a typed layer over existing standards, plus the one thing none of them covers: registries with a plugin manifest and permission checks. Every row below names the standard, the library that implements it (license), and what was rejected.

| Building block | Decision | Library (license) | Rejected, and why |
|---|---|---|---|
| Agent tools | **Model Context Protocol.** An `AgentTool` is an MCP tool definition (`name`, `title`, `description`, `inputSchema`, `outputSchema`, `annotations`) plus a handler. Helena serves every registered tool from its MCP endpoint. A plugin can also contribute a whole MCP server declaratively (`provides.mcpServers`), with no code at all. | `@modelcontextprotocol/sdk` 1.30 (MIT), already in the API | A Helena-specific tool format, the `@repo/agent-tools` `CustomToolEntry` (only internal agents could see those tools); OpenAI/AI SDK function-calling schemas (no annotations, no transport). |
| Action categories | The **MCP tool annotations** (`readOnlyHint`, `destructiveHint`, `openWorldHint`) are the basis. A tool that declares only annotations gets a category: read-only → `read`, destructive → `delete`, open-world → `send`, anything else → `write`. `execute`, `publish` and `pay` need an explicit `category` because the annotations cannot express them. When a tool is listed, the category travels as `_meta["helena/action"]`. A runtime's own tool calls map from the ACP `ToolKind` (`read/search/think/fetch` → `read`, `edit/move` → `write`, `delete` → `delete`, otherwise `execute`). | MCP spec 2025-06-18 annotations, ACP `ToolKind` | A separate risk score (the owner asked for categories); only annotations (these cannot say "pays" or "publishes"). |
| Runtimes | The target contract is the **Agent Client Protocol (ACP)**. The runner acts as the ACP client:<br>• starts the runtime's agent over stdio<br>• calls `session/new` (with Helena's MCP servers) or `session/load` (resume)<br>• sends `session/prompt`<br>• reads `session/update`<br>• answers `session/request_permission` through the policy<br>Today's presets stay as `cli` adapters until each runtime is proven over ACP. | `@agentclientprotocol/sdk` 1.5 (Apache-2.0); Hermes `hermes-acp` (in the Hermes tree); `@agentclientprotocol/claude-agent-acp` (Apache-2.0); `@zed-industries/codex-acp` (Apache-2.0) | Keeping one hand-written argv + stream parser per CLI (6 formats today, each breaks on CLI updates, and MCP and permissions are wired differently for each); A2A (agent-to-agent between services, not editor/harness control). ACP v2 (still a draft) is not used. |
| Chat/agent events for the UI | **AG-UI** events stay the stream format from the runner to the chat (already in use). Runtime adapters emit a normalized `RuntimeStreamEvent` whose variants mirror ACP `session/update`. The runner maps these to AG-UI. The web keeps the **Vercel AI SDK** (`ai`, `@ai-sdk/react`) for chat UI state. | `@ag-ui/core` 1.0 (MIT) as the reference for event types; `ai` 7 (Apache-2.0) | A new event format of our own. |
| Domain events | **CloudEvents 1.0**, structured JSON format. Helena attributes go in extension attributes: `helenateam`, `helenaproject`, `helenaactor`. Types are `helena.<noun>.<verb>`. | Own type (about 40 lines, conformant); the official `cloudevents` SDK is not a runtime dependency | `cloudevents` npm 10 (Apache-2.0) as a runtime dependency: it pulls in ajv, ajv-formats, json-bigint and the `util`/`process` polyfills for 5 fields, and it is not isomorphic (the web imports the types). A conformance test checks the attribute rules instead. |
| Event delivery | A **transactional outbox**: the event row is written in the same transaction as the change. The worker dispatcher fans each event out to one delivery per durable subscriber and retries each subscriber on its own. It is behind the `OutboxStore` interface, so it can move onto the queue that native-engine chooses (pg-boss / graphile-worker / DBOS). | Postgres, 2 tables | LISTEN/NOTIFY (lost while nobody listens); Kafka/NATS/Redis (extra service, violates rule 3). A cursor per consumer (bigserial ids commit out of order, so events get skipped). |
| Outgoing webhooks | **Standard Webhooks** signing (`webhook-id`, `webhook-timestamp`, `webhook-signature: v1,<base64 HMAC>`). The body is the CloudEvent. Webhooks become a durable event consumer. | `standardwebhooks` 1.1 (MIT) for verification in tests; signing is 5 lines with `node:crypto` | Keeping only the current `X-Itsaplan-Signature` (`t=…,v1=hex`, our own format). It stays for one release as a second header, so existing receivers keep working. |
| Schemas | **Standard Schema** for validation and **Standard JSON Schema** for describing a schema. Zod 4, Valibot and ArkType plug in directly. A plain JSON Schema (what TypeBox/Elysia and every MCP server produce) passes through unchanged. | `@standard-schema/spec` 1.1 (MIT, types only); zod 4 (MIT) | Zod-only (ties plugins to one library and one version); TypeBox-only (plugins would have to learn Elysia's schema library). |
| Plugin manifest | `helena.plugin.json`, validated by a **JSON Schema** (draft 2020-12). The schema is generated from the zod definition, so it cannot drift. | zod `toJSONSchema` | A `package.json` key like VS Code's (`contributes`) or Directus' (`directus:extension`): a separate file is clearer for plugins that are not npm packages (a folder with an MCP server). |
| Plugin model | Patterns borrowed from established systems:<br>• **VS Code**: declarative `contributes` → `provides`, and `engines.vscode` → `sdk` semver range.<br>• **Backstage**: plugin id, extension points, and a context/DI object in `register` instead of imports.<br>• **Strapi**: lifecycle `register` → `start` (bootstrap) → `stop` (destroy).<br>• **Directus**: split server and app entries, and flow "operations" as a model for step types.<br>• **Grafana**: unsigned plugins are only loaded from an allowlist; Helena pins id + version + sha256 digest. | `semver` 7 (ISC) | Module Federation / remote JS in the web app: it breaks `script-src 'self'` and couples plugins to our React/Next build. External UI therefore runs in sandboxed iframes. `vm` / `isolated-vm` sandboxes: false safety (`vm` is not a security boundary) or a native addon. The security model is documented instead (declared permissions, approval, digest pin). |
| Policy hook | One `decide({agent, project, action, context})`, shaped like a **Cedar/CASL** authorization request (principal, action, resource, context). Evaluators compose: the strictest decision wins, and when every evaluator abstains the request is allowed (today's behaviour). hub/autopilot picks the engine behind it. | none in the SDK | Choosing Cedar or CASL here: that is autopilot's decision; the hook fits both. |
| Knowledge | A `KnowledgeSource` contract: enumerate / get / events → items / resolve links, with ACL scope and provenance per item. A `CaptureTarget` handles "save to knowledge". hub/second-brain picks the index (Postgres FTS / pgvector / others). | none in the SDK | — |

## Consequences

- Plugins import only **types** from `@helena/sdk`. At runtime they get zod, the event bus and a logger through the context. So a plugin never carries a second copy of the SDK, and version skew shows up at load time (the `sdk` range), not as odd runtime errors.
- External web UI is iframe-only. Built-in UI uses components from the same slot registry.
- The runner can drive any ACP agent with one code path. Hermes, Claude Code and Codex switch one by one once each has been proven live (hub/hermes-sync, runner owners).
