# Volition integration

The integration service provisions project resources, runs inbox triage, and exposes an authenticated Connections API.

- Connections reports Hermes health. Only bounded probe actions are accepted.
- Inbox triage is read-only. Plan's worker starts a run with `POST /api/inbox/triage` and polls it with `GET /api/inbox/triage/:id`, using the inbox integration token. The thread's `account` must be one of the mail addresses in `INBOX_TRIAGE_ACCOUNTS`. The service validates the bounded, untrusted message data, hands it to a classifier and stores the validated JSON result. No classifier is built in: the Mastra `inbox-triage` workflow that classified threads was removed with Mastra, and a classifier on Hermes is an open item. Until then every run ends as `failed` with "No inbox classifier is configured." With `INBOX_TRIAGE_ACCOUNTS` empty, the triage routes answer `404`.
- Project provisioning (`POST /api/provision`) creates or removes a project's resources, once per event id. `GET /api/provision/state` reports the provisioning registry to the worker, which repairs differences from the database every ten minutes. `purge-trash.mjs` deletes expired trash entries; `native/systemd/volition-trash-purge.timer` runs it daily.
- Every agent in a provisioning request's `agents` list runs in a Hermes runtime of its own: the profile `profiles/<slug>_<agentId>` and the runner descriptor `run/agents/<slug>_<agentId>.json`, with the project's workspace as working directory and the project's browser. The agent id keeps the profile when the agent is renamed. The key comes from `POST /internal/bootstrap/project-agent` with the control token; Plan issues a new one only when the stored key no longer works. The runtime is the only holder of the key: a key Plan shows when the agent is created or its key is regenerated stops working once the runtime is keyed, and regenerating a key queues the provisioning again. Without a control token the service leaves agent runtimes as they are and reports a warning. A runtime whose agent is no longer in the list is removed: the descriptor is deleted because it holds the key, and the profile moves to the project trash. Each descriptor change writes a durable reload generation. The runner then stops taking new claims, finishes work already claimed, and exits so systemd starts it with a fresh descriptor catalog. A two-hour drain ceiling releases a stuck run to keep newly provisioned agents from waiting forever.
- Every area in a provisioning request's `areas` list has a folder of its own: `<workspace>/<folder>` and `<vault>/Projects/<KEY>/<folder>`. The registry lists the folder of each area and is written again after every folder that is trashed or moved, so a retry continues where a failed run stopped. A folder that changed is moved; when the new folder exists already, both stay and the result carries a warning. The folders of an area missing from the list move to the project trash with a receipt. A folder that existed before its area claimed it (`adopted` in the registry) is used as it is: it gets no `AGENTS.md` and is never moved or trashed. Every other workspace folder gets an `AGENTS.md` about its area when it has none. `GET /api/provision/state` lists an area only while both of its folders exist, so the worker's reconciliation recreates a missing one. Folders that belong to no area are left alone.
- Plan sends an agent only while it works in this one project. The runner claims an agent's runs from all of its projects with one working directory and one memory, so an agent that works in several projects has no runtime.

- With agent isolation (`AGENT_ISOLATION=on`, see `../isolation/README.md`) provisioning asks the root agent launcher to create the project's Unix user `vp-<slug>` and give it the workspace (ACLs for the runner and the readers group, with defaults), the agents' profiles and the vault folder: once before it writes into the workspace, once when every folder exists. A deleted project's user is removed; its UID is never given out again. The project browser's state is written by the browser user through the launcher (`project-browser-state.mjs`); the provisioning service starts and stops its units as before.

All bearer values are loaded from private files. Do not place credentials in this repository or service logs.
